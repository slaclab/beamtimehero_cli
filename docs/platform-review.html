§1The platform at a glance

The shape is sound and unusual in a good way: one library owns every beamline capability, and each application is a thin, differently-restricted view onto it.

The toolbelt declares 131 tool schemas, sorts them into nine top-level trees, and exposes them three ways: as a nested argparse command surface an agent can explore with --help, as exportable JSON schemas, and as an in-process dispatch function. Five applications consume it as an editable sibling install with no version pin. Nothing about the platform is speculative — it runs real beamtimes, and the scientific defaults are pinned by tests rather than left to drift.

The weaknesses are almost all at the seams rather than inside any one repo. Three consumers reach past the published four-symbol API into private internals, so the library has a public interface that nobody actually depends on and a private one that everybody does. And the boundary that keeps an agent away from hardware is a different mechanism in every application, which makes it hard to state in one sentence what any given agent can do.

§2beamtimehero_cli — the toolbelt

32,600 lines · 27 test files · CI on 3.11 and 3.13 · zero TODO markers

The scientific half of this repo is the best-organised code in the platform. Thirty-two modules sit under a science directory arranged by technique, nothing there reads an environment variable or opens a file, and nothing imports upward out of it. Every physics default lives in a policy module next to the functions that use it, and a test pins each constant by value, so moving a fit window or a convergence threshold is a deliberate two-line commit rather than a silent change. A generated index lists every science function with its signature, its citations, and which tools reach it. A scientist can be pointed at that directory with confidence.

The tool-catalog half is where the strain shows. Three files — the schema list, the provenance table, and the handler module — total 8,379 lines, a quarter of the source tree, and a single new tool has to be added to all three plus, sometimes, a fourth. A tool's name is written in up to five places. The tree is not declared anywhere; it is computed by a five-step precedence chain that falls back through a hand-maintained map of about seventy-five names, then infers the branch from whether the schema happens to require a justification argument.

High

Branch assignment is inferred, and one inference is also the safety classification. A mutating tool lands on the write branch because its schema lists justification as required. Drop that one string and the tool silently moves to the general branch, becomes reachable by agents that were never granted write access, and no test notices. The two facts — this tool mutates the beamline, and this tool needs a justification — should be one declared property, not one derived from the other.

Medium

Schemas and handlers are only related by convention. Every schema is hand-written JSON; every handler takes an untyped dictionary and pulls keys out of it. Nothing checks that the two agree, and nothing validates an argument before it reaches the function. A renamed parameter in one place and not the other produces a tool that runs with a silently missing value.

Medium

Profiles look like allowlists but are not a boundary. A profile adds an aliased branch onto the command surface; it never removes the canonical branches. Any agent that can run the command can still reach every tool, so restriction has to be imposed by whatever wraps the CLI. This is understood inside the repo, but the word "profile" invites the wrong assumption in the consumers.

Worth knowing

Two silent-failure paths. The dispatch table is built by importing the handler module inside a function that swallows import errors into an empty dictionary, so one bad import in one handler turns every tool into "unknown tool" rather than a traceback. Separately, a tool that runs and fails prints plain text and exits zero, which the agent integration document honestly flags — agents must not read the exit code.

Two smaller items: the category grouping used by consumer UIs has drifted badly, listing twenty-three tools that no longer exist while five real tools belong to no category, and it is the one part of the catalog no test covers. Thirty-five environment variables are read across the package, mitigated by a YAML config shim but still the widest configuration surface in the platform, and one of them is read but no longer used by anything.

The safety story is genuinely good where it is enforced. Justification text is checked for emptiness before a command reaches SPEC, the audit row is written before dispatch so a killed process still leaves evidence, and the justification is echoed into the SPEC session itself. The mock transport is the default, so a fresh clone cannot touch hardware. The operator's stop switch is enforced here as well, resolved per deployment and re-read on every call, and a switch file that exists but does not parse refuses writes rather than passing them.

§3autonomous — agentic beamline control

21,300 lines · 95 tests · no continuous integration · nine agent definitions

This is the highest-consequence application and, architecturally, the most interesting choice in the platform: the orchestrator is deterministic Python, not a model. A supervisor loop polls a SQLite plan store every three seconds and spawns the command-line agent as a subprocess per phase, one phase at a time, with no recursive delegation — every agent definition explicitly forbids spawning further agents. Sixteen tables hold experiment state, so nothing important lives in a context window, and a phase can be killed and resumed from its stored session. For a system that moves motors, putting the control flow in code and the judgement in the model is the right division.

The guardrails that exist are real and layered: a per-role motor allowlist that denies unknown roles by default, a human-intervention tool that blocks indefinitely until staff respond, a stop path that kills every phase process group, orphan purging at startup, and the mock transport forced on early in three separate entry points. Free-form SPEC strings are not available to role agents; they get whitelisted commands only.

High

The tool enable list is the wrong shape, and has frozen the feature set. A checked-in JSON file lists which tools are enabled, is intersected against the library's schemas, and fails open if absent. It was generated in early July and never regenerated. Thirty upstream tools are now invisible to every agent — the entire X-ray Raman branch, the EXAFS chi extraction and Fourier transform, edge identification, quality assessment, reference comparison — while thirty-two names in the file no longer exist. Science that was written, tested and documented is not reachable from the beamline that needs it.

Regenerating the file is not the fix. X-ray Raman and EXAFS work happens on different beamlines, so one agent will rarely want both branches, and a single global list cannot express that. The tool set belongs next to the per-role motor and write-tool sets that already exist, so each role sees the branch its science needs.

Medium

No budget of any kind. There is no turn cap, no cost cap, and no wall-clock limit anywhere in the repository, and the collection prompt instructs the agent to run until manually interrupted. Rate-limit failover exists, which handles the gateway saying no, but nothing bounds a productive loop that is doing the wrong thing.

Medium

Coupling to private internals, including live monkey-patching. The overlay imports the schema list and dispatch table directly, then patches two library modules at import time to substitute its own provenance table and executor. It works, and the 24 locally-defined tools genuinely overlay rather than duplicate — no name collides. But a refactor in the library that respects its published API can still break this repository, and there is no continuous integration here to catch it.

One asymmetry is worth naming for the sandbox discussion in §7. Arguments to the locally-defined tools are validated by typed models; the roughly 124 tools that come from the library are dispatched unvalidated. And the one unstructured-string surface in the whole system — a tool that evaluates an arbitrary SPEC macro — sits on the general branch, so it requires no justification, survives the role filter, and is available to every role. It routes into a disposable network-isolated container running simulation-mode SPEC, which is the right design; it is worth confirming that routing cannot be configured away on a production host.

§4chemcat — the multi-user portal

44,800 lines · 85 test files · required CI checks · five container images

Asked directly whether the containerisation is efficient and effective: yes, and it is the strongest security engineering in the platform. It is also the only place where the model runs behind a boundary a kernel enforces rather than a boundary the model is asked to respect.

Identity is Authentik OIDC with a mandatory group claim, and group membership is re-narrowed against the live roster on every request, only ever narrowing, with caches that fail closed. Data rows are keyed by user identifier, and conversations are siloed by a key derived from the authenticated session rather than any identifier the browser can name — there is no conversation id a user could tamper with. Each chat session gets its own pod: non-root, all capabilities dropped, read-only root filesystem, default seccomp profile, no service-account token, a twelve-hour hard deadline and an idle exit.

The two design decisions that carry the most weight are worth stating because they should be copied elsewhere. First, the child process environment is built from an explicit allowlist rather than inherited, so gateway keys and database URLs cannot leak into a process the model influences, and user notebooks are launched with an empty environment — there is no language model key in a user's notebook at all. Second, agent pods hold no database credentials; database-backed tools post through a broker that recomputes the caller's scope server-side and never trusts the pod's own copy of its scope file. The read-only workspace root is what makes it safe to allow arbitrary Python inside the pod, since an agent cannot rewrite the file that describes what it may read.

High

Network policy is not enforced by the cluster. The team has confirmed, not merely suspected, that the virtual cluster's networking layer ignores network policies — Postgres was reachable over TCP from an agent pod. Every policy in the repository is therefore correct by construction but inert. Credential hygiene is currently the real network boundary, and it is good enough that this is not a live exposure. It does mean the isolation story rests on one layer rather than two, and the same class of gap would be much more serious in a beamline-control context.

Medium

The contribution tiers are explicitly unenforced. The security document says so itself: the tiers are guidance designed against accident, not malice, and it names the concrete consequence — open-tier calculator code runs in the portal process and could read the session secret and forge a staff session. That honesty is admirable and the conclusion is unavoidable: this tier scheme cannot be the mechanism that lets strangers contribute. See §6.

Medium

Two portals, one codebase, parallel implementations. Two FastAPI applications share a database and a session secret under different base paths, with side-by-side sample, beamtime, staff, template and static trees. Two files named the same thing differ by seven lines. A separate module is a self-described keep-in-sync copy of a library data reader. This is the largest maintenance liability in the repo and the hardest thing for a newcomer to navigate.

Worth knowing

Supply chain and checkout hygiene. The agent image installs the command-line tool by piping an unpinned install script into a shell, which sits oddly beside otherwise careful pinning — every GitHub action is pinned by hash and the library is cloned at a fixed commit, though nothing automatically bumps that clone. Separately, a plaintext file in the operations checkout contains lines matching Slack token patterns; that is worth checking and rotating today rather than sometime.

§5The three lighter consumers

playground is the wide-capability assistant: a Streamlit and Slack front end over the command-line agent, allowed arbitrary Python, curl, wget, web search, web fetch and subagents, restricted only by a deny list in a settings file. It is effectively the low-guardrail research agent §7 asks for, already in use — but with no container boundary at all. It was also the last consumer of the library's pre-reorganisation import paths; those two files now import the real modules, and the compatibility shims are gone.

beamtimehero is the user-facing chat interface, running locally on the beamline machine for direct access to files, logs and the live SPEC session, with conversations mirrored to Slack for staff. It has been untouched since June while the platform around it moved four months; if it is still in service it is the least-reviewed door into the beamline computer, and if it is not, saying so in its README costs nothing.

autonomous_fourone is a BL4-1 port of the control system, forked in August as a full copy. Its README names the parent honestly, and the parent does not mention it at all. Two copies of a 21,000-line hardware-control application is the platform's most expensive open structural question: every fix to a guardrail now has to be made twice, and the §3 findings almost certainly apply to both. Deciding whether these converge onto one beamline-parameterised application, or divide permanently, is more consequential than any individual item in this report.

§6Readiness for outside contributors

For science code in the library: close, and better than most research groups ever get. For anything else: not yet, and the gap is mechanical rather than cultural.

What already works is substantial. The science directory has a stated rule, a layout by technique, and a table mapping "you want to change X" to "go to Y". The contributing guide names what is fair game without asking permission and names the three files to raise rather than edit. Physics defaults are pinned by tests, so a scientist changing a threshold gets a clear failure telling them to record the change, which is exactly the right teaching mechanism. Tests use synthetic spectra with analytic ground truth, so a contributor can write one without a beamtime. The linter is deliberately narrow — correctness only, no style opinions — so a first pull request does not get argued with about import order. Citations are a convention, and unattributed methods are recorded as explicit gaps rather than papered over.

Four things stand between that and a stranger's first pull request landing safely.

  1. A new tool costs five files and no test proves it worked. Adding science is easy; exposing it to an agent is not. The registration ceremony — schema, provenance, handler, sometimes a category map, then two regenerated documents — is the single biggest barrier, and it lands on exactly the boundary the guide marks off-limits. A scientist who writes a good analysis function currently cannot finish the job alone.
  2. The off-limits set is right but under-mechanised. It is stated in prose in one repository, while the blast radius of breaking it lives in five sibling checkouts that the library cannot see. A code-owners rule on those files, and a test that diffs the tool surface against a recorded baseline, would turn a social rule into a mechanical one.
  3. Contribution safety is guidance, not enforcement. chemcat says this outright, and its own example — open-tier code reaching the session secret — is the proof. In-process contributed code in an authenticated multi-user service cannot be reviewed by tiering; either it moves out of the process, or every contribution to it needs the same review as core code.
  4. The control repositories are not contributor-ready and should say so. autonomous has no continuous integration, a locally-ignored project instruction file, absolute paths from two different developers' home directories, and stray databases in its data directory. That is fine for a small trusted team and unfit for outside pull requests. Marking it internal-only for now is a better answer than a rushed cleanup.

The highest-leverage change is the first one. If registering a tool were derived from the handler — one typed function with a docstring and a declared branch, from which the schema, the provenance entry and the documentation are generated — then the off-limits set would shrink to something a contributor never has to touch, the schema-handler mismatch in §2 would become impossible, and the drifting category map would have no separate copy to drift from. That is a substantial refactor of the largest files in the platform, and it is the one that pays for itself in every other finding here.

§7A sandbox for unguarded queries

The good news is that this has largely been designed and built already, in chemcat, and the local ingredients exist on the beamline host. The work is porting, not inventing.

The requirement: the control system should be able to hand a hard analysis question to something that may run arbitrary Python and reach the web, without that something being able to touch hardware, disturb an ongoing collection, or hold any credential that matters. Two existing pieces answer most of it.

chemcat's agent sandbox is the pattern. A second settings file keeps the deny spine — no web, no git, no curl, no remote shell, no environment-prefix smuggling, no write branch, no database, no messaging — and adds arbitrary Python plus writes confined to three working directories. The insight the design document states explicitly is the one to carry over: moving execution somewhere a kernel can enforce the boundary is precisely what makes it safe to widen the allowlist. The read-only workspace root is load-bearing, because a writable scope file would let the agent widen its own containment.

The second piece is already running on the beamline host: the SPEC macro evaluator, a small local service that spawns a fresh container per request with no network, one CPU, two gigabytes, a hard timeout and automatic removal. That is the right shape for a local disposable sandbox, and reusing its service contract means the calling side is a familiar tool invocation rather than new infrastructure.

What to build

A local research-sandbox service on the same host, called through one new tool that takes a question and returns a written report with its figures. Concretely:

  • Isolate by absence, not by permission. No SPEC variables, no transport configuration, no database URL, no Slack token in the container environment — built by allowlist as chemcat does, never inherited. This is what makes the §4 finding about unenforced network policy survivable there, and it is the property to copy first.
  • Mount one experiment's scan directory read-only plus a writable scratch for figures and notes. The sandbox reads data; it never writes where the collection writes.
  • Allow web search and fetch, with egress restricted to the gateway and outbound HTTPS only. Note that chemcat deliberately left these denied pending an exfiltration review. The calculus is different here and worth writing down: what is reachable is one experiment's own scans, visible to the staff asking the question, rather than another user's private data. That makes it defensible, but the decision should be recorded rather than inherited by accident.
  • Give it a real budget. Wall clock, turn count, and token spend, enforced by the service. §3 notes the control system has none of these today; an arbitrary-Python agent with web access is the wrong place to discover that.
  • Audit the question and the answer into the same log as everything else, so a sandbox consultation appears in the experiment record alongside the actions it informed.
  • Make it a tool, not a delegate. The calling agent gets a report back and remains the only thing that can act. Nothing in the sandbox should be able to enqueue a motor move, directly or by writing somewhere the control system reads.

A closing observation that the individual findings do not capture. Every serious problem here is a place where two descriptions of the same fact were allowed to drift apart: a schema and its handler, a tool list and the tools, two portals, two beamlines. The platform's own best idea is the answer to all of them — the science directory has one copy of each default, pinned by a test that fails when it moves. Applying that discipline to the tool surface is the through-line of this report.
